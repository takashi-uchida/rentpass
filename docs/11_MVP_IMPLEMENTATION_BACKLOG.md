# RentPass MVP 実装バックログ

このドキュメントは、RentPass を「事業構想・画面設計」から「動くMVP」へ進めるための実装単位を整理したものです。

## MVPの到達点

MVPでは、物件検索ポータルを作るのではなく、管理会社・仲介会社が審査困難な申込を受けたときに、入居希望者の信用パスを作成し、受け入れ条件を設計し、オーナーへ入居安心レポートを共有できる状態を目指します。

```text
紹介された物件
  ↓
入居希望者が信用パスを提出
  ↓
管理会社が本人確認・支払い・見守り・緊急連絡先を確認
  ↓
受け入れ条件ビルダーで条件を組む
  ↓
オーナー向け入居安心レポートを生成
  ↓
条件付き承認
  ↓
契約準備・入居後見守りへ
```

## 実装Epic

| Epic | 目的 | 優先度 |
| --- | --- | --- |
| E1: 入居希望者信用パス | 入居希望者が必要情報を提出できる | P0 |
| E2: 管理会社申込レビュー | 管理会社が申込を確認し、条件設計に進める | P0 |
| E3: 受け入れ条件ビルダー | 前払い・保証・見守り・緊急連絡条件を組める | P0 |
| E4: オーナー向け入居安心レポート | オーナーが条件付き承認できる | P0 |
| E5: 入居後見守り | チェックインと未応答アラートを管理できる | P0 |
| E6: Supabase/RLS | 役割ごとにデータを安全に分離する | P0 |
| E7: 外部サービス連携スタブ | eKYC・保証・収納・信託のステータスを扱える | P1 |
| E8: テスト・CI | 型検査、ビルド、主要フローの回帰を守る | P1 |

## Issue分割

### MVP-01 入居希望者の信用パス作成フロー

対象画面:

- `/tenant`
- 信用パスダッシュボード
- 本人情報入力
- 本人確認ステータス
- 収入・資産情報
- 前払い・支払いプラン
- 緊急連絡先
- 見守り設定

受け入れ条件:

- [ ] 信用パス完成度をパーセント表示できる
- [ ] 必須項目の完了/未完了が一目で分かる
- [ ] 入居希望者は「紹介された物件」に対して信用パスを提出できる
- [ ] 職業名ではなく、支払い能力・前払い・連絡体制・見守り体制を中心に表示する
- [ ] 同意前にオーナーへ詳細情報を開示しない

### MVP-02 管理会社の申込レビュー画面

対象画面:

- `/management`
- 申込一覧
- 申込詳細
- 書類確認
- 支払い確認
- 見守り確認
- 緊急連絡先確認

受け入れ条件:

- [ ] 新規申込、書類確認待ち、条件設計中、オーナー確認待ちを一覧で確認できる
- [ ] 申込詳細で本人確認、資産確認、前払い、見守り、緊急連絡先の状態を確認できる
- [ ] 不足情報に対して追加提出依頼を作成できる
- [ ] 管理会社はオーナーに見せる情報と内部確認情報を分けて確認できる

### MVP-03 受け入れ条件ビルダー

対象画面:

- 支払い条件設定
- 見守り条件設定
- 緊急対応条件設定
- 保証・保険条件設定
- 推奨条件サマリー

受け入れ条件:

- [ ] 前払い月数を選択できる
- [ ] 保証会社必須/任意/不要を選択できる
- [ ] 見守り頻度と未応答判定時間を選択できる
- [ ] 緊急連絡先の必要人数を設定できる
- [ ] 孤独死保険・残置物処理・家財保険の推奨状態を持てる
- [ ] 設定した条件からオーナー向けレポートを生成できる

### MVP-04 オーナー向け入居安心レポート

対象画面:

- `/owner`
- 入居安心レポート
- 条件付き承認
- 条件追加依頼
- 見送り

受け入れ条件:

- [ ] オーナーは詳細な通帳画像や健康情報を見ずに、対策済み項目だけで判断できる
- [ ] 推奨受け入れ条件を1枚で確認できる
- [ ] 「承認」「条件追加」「見送り」の判断を記録できる
- [ ] 管理会社側に判断結果が戻る

### MVP-05 入居後の見守り・安否確認

対象画面:

- 入居者チェックイン
- 見守り状況一覧
- アラート詳細
- 対応ログ

受け入れ条件:

- [ ] 入居者は「元気です」「相談したい」を選択できる
- [ ] 管理会社は正常/未応答/対応中/解決済みを一覧確認できる
- [ ] 未応答時に本人再通知、緊急連絡先通知、管理会社対応の段階を記録できる
- [ ] 対応ログには誰がいつ何をしたかが残る

### MVP-06 Supabase 認証・RLS・監査ログ

対象領域:

- Auth
- tenants
- management_companies
- owners
- lease_applications
- assurance_conditions
- check_in_events
- alerts
- audit_logs

受け入れ条件:

- [ ] tenant / manager / owner のロールを分離する
- [ ] 入居希望者は自分のデータだけ閲覧・更新できる
- [ ] 管理会社は自社管理の申込だけ閲覧できる
- [ ] オーナーは共有された入居安心レポートだけ閲覧できる
- [ ] 重要情報の閲覧・更新は audit_logs に記録される

### MVP-07 外部サービス連携スタブ

対象連携:

- eKYC
- 保証会社
- 収納代行
- 信託会社/家賃リザーブ
- SMS/LINE通知
- 保険会社

受け入れ条件:

- [ ] 外部連携は本番API直結ではなく、まずステータスモデルとスタブで扱う
- [ ] eKYCは `not_started / pending / verified / rejected` を持つ
- [ ] 保証会社は `not_applied / applying / approved / rejected` を持つ
- [ ] 家賃リザーブは `not_used / proposed / deposited / releasing / completed` を持つ
- [ ] RentPassは資金を保持しない設計であることを画面とモデルに反映する

### MVP-08 主要フローのテストとCI強化

対象:

- TypeScript 型
- ビルド
- 主要ユースケースのコンポーネントテスト
- RLS方針のSQLテスト

受け入れ条件:

- [ ] `npm run typecheck` が通る
- [ ] `npm run build` が通る
- [ ] 申込作成からレポート生成までの主要状態遷移をテストできる
- [ ] 見守り未応答から対応ログ作成までの状態遷移をテストできる
- [ ] RLS違反になる操作をテストケースとして持つ

## 実装順序

1. 型とモックデータを固める
2. 入居希望者信用パスを実装する
3. 管理会社申込レビューを実装する
4. 受け入れ条件ビルダーを実装する
5. オーナー向けレポートを実装する
6. 入居後見守りを実装する
7. Supabase連携を本実装へ移す
8. 外部サービス連携をスタブから実APIへ差し替える

## MVPでやらないこと

- 本格的な物件検索ポータル
- AIによる自動審査/スコアリング
- RentPass自身による資金預かり
- 自社保証
- 自社での駆けつけ/死後事務
- 詳細な健康情報のオーナー開示

MVPの芯は、あくまで「審査を甘くする」ことではなく、「貸せる条件を設計し、説明可能にする」ことです。
